# 共有セッションの容量・無料枠モデル

更新日: 2026-11-18

この文書は実測負荷試験の結果ではない。コードに設定された上限、Supabase Freeの公開料金・制限、保守的な通信量仮定から算出した運用目安である。応答時間、同時アクセス時のDB CPU、月次実使用量を保証するものではない。

## 結論

| 項目 | 運用目標 | 根拠 |
|---|---:|---|
| 公開閲覧RPC | **450回/日、13,500回/30日** | 1回68KiBで約0.94GB/月 |
| この機能に割り当てる未キャッシュEgress | **約1GB/月まで** | Freeの5GB未キャッシュ枠の約19%。残りを同一組織の他サービスへ確保 |
| 編集者Realtime接続 | **100接続までを目安** | Freeの200 peak connectionsに対して半分を残す。20人満員の共有スペースなら同時5室 |
| Realtimeメッセージ | **50万件/月を目安** | Freeの200万件の25% |
| フル参加20名の保存イベント | **約23,809回/月までが上記50万件の理論値** | 1保存につき送信1件 + 最大20受信者 = 21件 |
| Realtime停止中の編集poll | **60秒（操作直後）/120秒（アイドル）** | 旧30/60秒から半減し、障害時のDB要求を抑える |

ここに記載する450回/日や100接続は**アプリケーションで強制するハード上限ではなく、運用上の予算**である。現在、公開読み取りRPCにIP単位のレート制限やCDNキャッシュはない。自動化された連続アクセスはブラウザの60秒キャッシュを回避できる。

## 1. 公開閲覧の転送量

### 1回あたりのサイズ

公開読み取りRPC `read_public_party_session` が返すのは、セッション名、編成キー、選択された追加人格スナップショット、revision、発行者表示名、公開設定などに限定される。メンバー一覧や編集履歴は返さない。

追加人格スナップショットは、編集RPCでJSON文字列化した合計が60,000 bytesを超えないよう検証される。1編成は最大20枠で、公開読み取りには最大20個の人格キーと応答メタデータも付く。このため、見積もりでは圧縮を一切見込まず、JSON外枠・キー・ヘッダーの余裕を含め **68 KiB = 69,632 bytes/取得** とする。

本番DBに現在ある5スペースの照合では、`party_personas::text` の最大は1,644 bytes、編成キーの最大は3件だった。ただし既存行は通常利用の現状値に過ぎず、最大20枠・60KBの将来データを代表しないため、上の68KiBを予算計算に使う。

### 月間リクエスト別の未キャッシュEgress

前提: 30日/月、全リクエストが68KiB、HTTP圧縮による削減なし、全アクセスがキャッシュミス。単位GBは10進数。

| 平均閲覧取得 | 月間RPC | 未キャッシュEgress概算 |
|---:|---:|---:|
| 100回/日 | 3,000回 | 0.209 GB |
| 250回/日 | 7,500回 | 0.522 GB |
| **450回/日** | **13,500回** | **0.940 GB** |
| 500回/日 | 15,000回 | 1.044 GB |
| 1,000回/日 | 30,000回 | 2.089 GB |
| 2,500回/日 | 75,000回 | 5.222 GB |

Freeの未キャッシュEgress 5GBをこの機能だけで使う場合の理論上限は約71,806回/月である。しかし、この値を運用目標にしてはいけない。SupabaseのEgress枠は組織単位で合算され、Database、Auth、Storage、Functions、Realtimeなど複数サービスが使う。また、Database RPCの応答は未キャッシュEgressとして扱う。別枠のCached Egress 5GBをこのRPCに流用できるとは見なさない。

したがって、この機能の月間目標を約1GB（450回/日）に置き、残り約4GBは同じ組織内の他プロジェクト・Auth・Realtime等のために確保する。実際に他サービスが使える残量はDashboardの組織全体の使用量で変わるため、1GBを確保できない月は公開範囲を狭める。

### キャッシュと悪用耐性

- 公開閲覧は初回取得後に自動poll・Realtime接続をしない。
- 同じブラウザタブの `sessionStorage` に最大60秒保存する。同じタブで60秒以内に開き直す場合の再取得を減らす。
- 「編成を更新」はキャッシュを迂回する。別タブ・別ブラウザ・別ユーザーのキャッシュは共有されない。
- 公開RPCは匿名で呼び出せるため、スクリプトから直接呼び出せばブラウザキャッシュを回避できる。CAPTCHAは新規Anonymous Auth作成を保護するが、匿名閲覧RPC自体のIPレート制限ではない。
- CDNキャッシュ・IPレート制限・月間自動遮断は未実装。450回/日は目標であってコードによる停止保証ではない。

## 2. 編集者Realtimeの通信量・接続数

Supabase Freeの現行公開値は、Realtime Messages 2,000,000件/月、Peak Connections 200、メッセージスループット100件/秒。RealtimeのBroadcastは送信1件に加え、受信した各購読クライアントにつき1件として数える。

このアプリは変更本体をBroadcastせずrevision番号だけを送る。編集参加者の上限は発行者を含め20名。1つの保存イベントを最大20クライアントが受け取る場合、送信1 + 受信20 = **最大21メッセージ**と見積もる。

- Free枠2,000,000件を全てこの機能で使う理論値: 2,000,000 / 21 = 約95,238保存/月。
- その25%に相当する500,000件を本機能の目標予算にすると、約23,809保存/月。
- 100件/秒のスループットを最大21件/保存で割ると、満員室の連続保存は理論上約4.76回/秒が上限目安。実際にはPostgresの行ロック、revision競合、ネットワーク等も影響するため、これを保証性能とは扱わない。
- Peak Connections 200を全て使い切らず、運用目標を100接続に抑える。1室20名満員なら同時5室相当。残り100接続を同一組織の別用途・ブラウザ複数タブ・予備に残す。
- 100接続は現在コードで強制していない。200接続を超えるとRealtime接続失敗が起こり得て、編集者はpoll fallbackに依存する。

閲覧者はRealtimeへ接続しないため、閲覧者数を増やしてもRealtime接続数やBroadcast受信数は増えない。

## 3. Realtime停止時のpoll fallback

Realtimeが利用できないときだけ、編集画面は60秒（操作直後）/120秒（アイドル）のpollへ切り替える。非表示タブは停止する。公開閲覧者には適用しない。pollのrevisionが変化していなければDB関数は小さな `unchanged` 応答を返すため、毎回68KiBのスナップショットを返す計算ではない。一方、毎回Postgres RPCを呼ぶため、データ転送が小さくてもDB要求数は増える。

20人の編集者が全員アクティブのまま60秒pollを30日続けると、1室で約864,000 RPC/月。100接続（満員5室）で約4,320,000 RPC/月、Free peak connectionsの200接続を全て使う10室なら約8,640,000 RPC/月となる。全員アイドルで120秒pollならこれらの約半分となる。

これはRealtimeが長期間使えず、全編集者のタブが表示状態で継続稼働する極端な計算である。通常はRealtime通知を使う。長時間poll fallbackが続く状態は通常運用として想定せず、同期が不安定なら共有編集を一時停止して設定・Realtime状態を確認する。

## 4. 運用上の判断基準

| 状態 | 判断 |
|---|---|
| 本機能の公開読み取りが約1GB/月以下 | 想定予算内。ただし組織全体の未キャッシュEgressも確認 |
| 組織全体の未キャッシュEgressが4GB/5GB（80%）に到達 | 新規の広範な公開を止め、どのプロジェクトが増加させているか確認 |
| 組織全体の未キャッシュEgressが4.5GB/5GB（90%）に到達 | 高トラフィックの共有リンクを公開停止し、翌サイクルまで余裕を確保 |
| Realtime接続が継続的に失敗しpoll fallbackが続く | 共有編集の新規参加を止め、Dashboard設定・接続・ポリシーを確認 |

Supabase Freeでは枠超過時に猶予期間やサービス制限が発生し得る。無料枠を超える利用を当然の前提にしない。

## 5. 既知の制約

- 450回/日、100 editor connections、50万Realtime messages/月は運用予算であり、アプリ内で強制するハードリミットではない。
- 公開read RPCのIPレート制限、CDN、グローバルな月間リクエスト遮断は未実装。
- 他のプロジェクト・サービスが使うEgress/Realtime枠は本機能側から予約・固定できない。
- 100/1,000同時閲覧、長時間Realtime停止、実際のJSON転送量・DB応答時間・CPUを測った負荷試験はしていない。ここにある値は上記前提に基づく算術モデルである。
