# 共有セッション機能の設計案

## 目的

現在の PARTY COLOR BOARD は静的サイトで、編成内容を URL / `localStorage` に保存する。URL は編成のスナップショット共有には使えるが、他の人の編集内容は同期されない。

次の構成で、セッションごとに独立した編成を持ち、共有リンクを開いた共同編集者が同じ状態を編集できるようにする。

## 推奨構成

- **フロントエンド:** 現行の GitHub Pages を維持。人格 DB と集計ロジックは既存資産を引き続き使う。
- **バックエンド:** Supabase（Postgres、Auth、Realtime、Edge Functions）。
- **セッション境界:** 編成データはセッション ID ごとに保存し、URL とブラウザのローカル状態をセッションの正本にしない。
- **リアルタイム状態:** Postgres の更新を購読して編成・集計を更新し、Realtime Presence でセッションに接続中の人数や参加者を示す。
- **認可:** 招待リンクのトークンは十分な長さの暗号学的乱数で作り、DB にはトークン本体ではなくハッシュを保存する。リンクの検証と参加登録は Edge Function で行い、ブラウザに service-role / secret key を渡さない。公開テーブルには RLS を有効化し、会員でない利用者の読み書きを拒否する。

## 主要フロー

1. 「セッションを作成」で名前を付けた空の編成セッションを作る。
2. 「編集リンクを発行」でリンクを作る。リンクを開いた利用者は、匿名 Auth セッションを取得したうえで招待トークンを検証し、対象セッションの editor メンバーとして登録される。
3. セッション内の追加・変更・削除はサーバーの RPC を通し、DB のトランザクション内で検証して保存する。
4. 保存が確定したら Realtime で他の画面へ通知し、人数・資源色サマリー・マトリクス・人格詳細を同時に再描画する。
5. セッション作成者には、編集リンクの無効化・再発行、セッションの名前変更・削除などの管理操作を提供する。

## データモデル案

- `sessions`: `id`, `title`, `owner_user_id`, `party_keys`, `revision`, `created_at`, `updated_at`, `archived_at`
- `session_members`: `session_id`, `user_id`, `role`（owner / editor / viewer）, `joined_at`
- `session_invites`: `id`, `session_id`, `token_hash`, `role`, `expires_at`, `revoked_at`, `created_at`
- `session_events`: `id`, `session_id`, `actor_user_id`, `operation`, `payload`, `revision`, `created_at`

編成キーは既存どおり人格キーだけを保存し、人格名や罪悪色を重複して保存しない。表示用の人格情報は既存の `data/personas.json` から導出する。

## 同時編集・データ整合性

- 各書き込みはサーバー側のトランザクションで処理し、`revision` を単調増加させる。
- RPC で「追加」「交換」「削除」「クリア」を操作として処理し、サーバー側で人格キーの有効性、重複、現行の最大6枠を検証する。
- 古いリビジョンを基にした更新を無条件に上書きしない。更新競合時は最新状態を読み直し、利用者に同期済み状態を示す。
- 操作履歴を `session_events` に残し、誰が何を変更したかと直近の変更を後から確認できるようにする。
- Sort 設定など表示だけの好みは、原則として利用者ごとのローカル設定に残す。共有対象は編成の実データとセッション名を中心にする。

## 共有リンクと権限

リンクを持つ人を編集可能にする方式は「秘密リンクを持っていること」を権限とする bearer-token 方式になる。リンクは転送できるため、**リンクを開いた本人だけ**と厳密には保証できない。漏れた場合に作成者が即時失効・再発行できるようにする。特定の人物だけに限定する必要が出た場合は、アカウントや許可リストを追加する。

トークンは URL の fragment（`#...`）などを使って不要なサーバーログへの露出を抑え、検証後はブラウザ履歴から取り除く。トークン自体を分析ログやエラーメッセージへ書かない。セッションの読み取りも公開にはせず、参加登録済みの会員に限定する。

## 制限とスケール

アプリ独自の「参加者は最大 N 人」「セッションは最大 N 個」という固定制限は設けずに実装できる。ただし、クラウド側の同時接続数、メッセージ量、DB 容量、帯域、料金にはプランごとの上限があるため、インフラ上の制限を完全になくすことはできない。無料枠で試験運用し、実測した利用量に応じて有料プランまたはセルフホストを検討する。招待トークンの失効、レート制限、荒らし対策も必要。

## 実装順序

1. セッション作成・一覧・削除と空のセッション保存
2. 招待トークン・匿名参加・RLS / Edge Function の権限テスト
3. 編成操作をトランザクション化し、競合と重複をテスト
4. Realtime 購読とオンライン参加者表示
5. 変更履歴、リンク失効・再発行、エラー時の復旧導線
6. データ保持期間、バックアップ、レート制限、利用量監視

## リリース条件

- 非参加者がセッション内容を読み書きできないことを自動テストする。
- 失効済み／期限切れリンクが参加登録できないことをテストする。
- 複数ブラウザで追加・変更・削除を同時に実行しても、重複や不正な編成にならないことをテストする。
- 接続切断後に再接続した際、サーバーに保存された最新の編成へ復帰することを確認する。
- GitHub Pages のキーに管理者権限を持たせない。service-role / secret key はフロントエンドへ埋め込まない。
