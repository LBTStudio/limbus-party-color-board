# 共有セッション機能の設計

## 状態と目的

**共有セッションは実装済み**。Supabase の migration / Anonymous Sign-Ins / publishable key を設定すると有効になる。未設定の間は GitHub Pages 上の個人用編成（URL / `localStorage`）だけが動く。

この設計は「編成作業の補助」を優先する。チャットや共同描画のようなサブ秒同期は不要で、共有する実データも最大6人分の人格キーとリビジョン程度である。一方、誤編集、編成の消失、他グループへの漏えいは避けなければならない。

## 決定事項

1. **グループごとに別セッション**を作り、各リンクは必ず1セッションだけを指す。セッション ID、メンバー、編成状態、revision、編集履歴を別々に保持する。
2. **デフォルトは非公開**。リンクを開いただけでは編成・参加者・履歴を取得できない。リンクはアクセス申請の入口であり、申請者は発行者（owner）が承認するまで読み書きできない。
3. **owner が権限を管理**する。申請の承認・却下、editor / viewer の付与、メンバーの剥奪、招待リンクの失効・再発行、セッションのアーカイブを提供する。
4. **通信の初期方式は軽量ポーリング**。WebSocket / Realtime Presence は初期版では使わない。編成用途では数秒の反映遅延を許容し、実装・接続管理を簡素化する。
5. **共有状態の正本はサーバー**。クライアントの表示は楽観的に更新できるが、確定した編集はサーバーの応答後とする。セッションがオフライン時にローカルだけで編集確定したように見せない。
6. **既存の集計はクライアントで継続**。ネットワークで送るのは人格キー、revision、最小限の編集メタデータのみ。人格 JSON、色集計、表の DOM、並べ替えや選択色は送らない。

## 推奨構成

- **フロントエンド:** GitHub Pages と既存の JS モジュール、人格データ、集計ロジックを維持する。
- **保存・認可:** Supabase Postgres / Auth / RLS。書き込みはトランザクションを保証する RPC で行う。
- **招待と権限管理:** 少数回の高権限操作（招待の発行・検証、参加申請、承認・却下、役割変更、剥奪）は Edge Function または厳密に制限した RPC を使用する。
- **同期:** メンバー認可付きの軽量 DB RPC / REST エンドポイントで revision を確認する。ポーリングのたびに Edge Function を呼ぶ構成は避ける。ポーリング応答は「変更なし」なら revision など最小情報だけ、「変更あり」なら最新版の編成を返す。
- **秘密鍵:** browser に service-role / secret key を含めない。公開キーが必要な場合も、RLS とテーブル権限を正しく構成する。RLS はテーブルごとに有効化し、grant と policy の両方を監査する。

参考: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)、[Supabase Edge Function 認証](https://supabase.com/docs/guides/functions/auth)、[HTTP conditional requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests)。

## セッションとデータ境界

概念データモデル:

- `party_sessions`: `id`, `title`, `owner_user_id`, `party_keys`, `revision`, `created_at`, `updated_at`, `archived_at`
- `session_members`: `session_id`, `user_id`, `role`（owner / editor / viewer）, `joined_at`
- `session_invites`: `id`, `session_id`, `token_hash`, `expires_at`, `revoked_at`, `created_by`
- `session_access_requests`: `id`, `session_id`, `user_id`, `display_name`, `status`（pending / approved / denied / revoked）, `requested_at`, `decided_by`, `decided_at`
- `session_events`: `id`, `session_id`, `revision`, `actor_user_id`, `operation_id`, `operation`, `created_at`

セッション間の境界は UI だけに依存しない。メンバー、招待、申請、編集、履歴の全行に `session_id` を持たせ、キー制約と全サーバー処理をセッション単位にスコープする。セッション A のリンクや revision を使ってセッション B の内容を読んだり編集したりできないことを RLS / RPC の自動テストで保証する。

保存する編成は `party_keys`（人格キーの順序付き配列）のみ。人格名、罪悪属性、各種集計は `data/personas.json` から導出する。サーバーはクライアントから受け取ったキーを信用せず、リリース済みの人格キー許可リスト、重複なし、最大6名を検証する。Sort、選択色、検索語など表示上の好みはユーザーごとのローカル設定とし、他メンバーの表示を勝手に変えない。

## 招待・参加権限の流れ

1. owner が認証して空のセッションを作成する。セッション URL / ID は秘密情報として扱わない。
2. owner が有効期限付き招待リンクを発行する。リンクの fragment（実装は `#invite=<random-token>`）には十分長い暗号学的乱数を置き、DB には token 本体ではなくハッシュを保存する。秘密トークンはログやエラー、計測イベントへ出さない。
3. 訪問者はリンクを開いて表示名を入力し、アクセスを申請する。トークンは申請の資格を示すだけで、編成データへのアクセスを直接与えない。トークンを使う処理は HTTPS でサーバーへ送り、処理後は `history.replaceState` で URL から除く。
4. owner は申請者を確認して却下するか、viewer / editor として承認する。承認前の申請者に、編成、メンバー一覧、履歴、セッション名など非公開情報を返さない。
5. owner はいつでもメンバーを剥奪し、リンクを失効できる。以降のサーバー要求は拒否される。ただし剥奪前に本人が閲覧・コピーした情報を遠隔から回収することはできない。
6. 「このリンクを受け取った人」と「想定した本人」が同一であることは、秘密リンクだけでは保証できない。匿名表示名は本人確認ではない。人物単位の確実な識別が必要な運用では、承認前にメール検証または OAuth などの認証を必須にする。

## 通信方式

### 読み取り

- 承認済みセッションを表示中のタブのみポーリングする。招待ページ、未承認ユーザー、セッション外では行わない。
- 初期値は「操作または revision 変更から2分以内の表示タブ: 5秒間隔」「それ以外の表示タブ: 15秒間隔」「非表示タブ: ポーリング停止」。タブ復帰、ネットワーク復帰、手動再読込時は即座に最新状態を確認する。
- request を重ねて発行しない（in-flight guard）。タイミングに jitter を加え、同時接続者全員が同時刻にアクセスするのを避ける。
- ポーリング要求には `session_id` と既知の `after_revision` を含める。認可・revision 確認をサーバー側で行い、変更なしなら最小応答、変更ありなら最新版スナップショットを返す。クライアントは revision が古い応答で画面を巻き戻さない。
- ブラウザや CDN の古い応答で共有状態が戻らないよう、共有状態 API はキャッシュしない。HTTP ETag / 304 が利用可能な経路では転送量を抑えるが、初期実装を特定プロバイダーの ETag 対応に依存させない。
- 連続失敗は指数バックオフ（例: 5秒 → 10秒 → 20秒、最大60秒）とし、レート制限応答の `Retry-After` を尊重する。エラー中に短い間隔で再試行し続けない。

### 書き込み

- 追加・交換・削除・クリアを小さな操作として送る。クライアント側だけの表示変更はネットワークへ送らない。
- 操作要求には `session_id`, `expected_revision`, 一意な `operation_id` を含める。
- サーバーは1トランザクションで、メンバーと role、セッションの状態、revision、人格キーの有効性、重複、最大6名を検証し、更新と event 追加を同時に行う。
- 成功時は確定 revision と最新版を返す。同じ `operation_id` の再送は二重適用しない。期待 revision が古い場合は競合として拒否し（HTTP API 層では 409 相当）、最新状態を読み直して利用者に示す。古いスナップショットを無条件で全置換しない。
- viewer の書き込み、editor のメンバー管理、非メンバーの読み書き、別セッションへの越境アクセスはサーバーで拒否する。

## 通信量の見積もりと調整

ポーリングは Realtime メッセージ配信を使わない代わりに、変更がなくても確認要求が発生する。「ポーリングなら無制限・常に安い」とは見なさず、実測で間隔を調整する。

- 5秒間隔: 1クライアントあたり12要求/分。
- 15秒間隔: 1クライアントあたり4要求/分。
- 非表示タブを停止すると、その間の定期要求は発生しない。復帰時に1回同期する。
- 仮に1人が1日30分、月20日、全時間を5秒間隔で利用すると 360要求/日/人、**7,200要求/月/人**。同条件100人なら約720,000要求/月。要求数は概算で、認証・保存・参加管理の API 要求は別途加算される。
- 確認要求は小さくしてもリクエスト数と DB 評価コストは残る。応答量だけでなく、DB read、帯域、失敗率、revision が変わった回数を計測する。低利用であれば軽量ポーリングを採用し、参加者数や同時閲覧が増えて計測値が閾値を超えたら Realtime / 長いポーリングへの移行を検討する。固定の参加人数制限を先に設けるのではなく、プロバイダーの実上限と監視で判断する。

## 編集競合と操作体験

- `revision` は**セッションごと**に単調増加させる。1グループの更新で別グループの revision が変わらない。
- 競合時に last-write-wins で上書きしない。最新スナップショットを表示し、再適用できる操作と利用者が判断すべき操作を分ける。
- UI では「保存中」「保存済み」「同期中」「接続なし」「権限が失効」「競合が発生」を区別する。サーバー応答前に保存済みと表示しない。
- サーバーに到達できない時はローカルの未送信操作を確定済みと偽らない。未送信の変更を破棄する前に警告し、必要に応じて TSV / URL へ退避させる。
- 履歴に保存する操作データは必要最小限とし、保持期限と owner によるセッション削除を定義する。

## 主な失敗想定とリリース前確認

詳細な失敗シナリオ、発生条件、予防策、検証項目は [共有セッションの失敗想定と対策](shared-sessions-failure-modes.md) を参照する。少なくとも、未承認アクセス、リンク漏えい、権限剥奪、セッション混線、同時編集、応答消失後の再送、ネットワーク断、タブ休止、期限切れ・削除済みセッション、429 / 5xx、プロバイダー上限を試験する。

## リリース条件

- 未承認者・非メンバーはセッション内容とメンバー一覧を一切読めない。
- A のメンバーは B を読めず、A 用の招待・revision・operation ID で B を変更できない。
- invite を失効した後は新しいアクセス申請に使用できない。member の剥奪後は新しい読み書き要求が拒否される。
- editor だけが編成を書け、viewer は読み取りのみ、owner 操作は owner のみ実行できる。
- 同時編集で重複や6名超過、無言の上書きが発生しない。同じ operation ID の再送で二重反映しない。
- オフライン・タブ休止後に最新 revision に戻り、保存確認前に「保存済み」と表示しない。
- 共有 API にキャッシュが混じらず、未承認ユーザーが大量要求してもデータを取得できず、要求が制限される。
- CI で RLS / role / session isolation / concurrent revision / invitation lifecycle を自動試験する。
- GitHub Pages のビルド成果物に service-role / secret key が含まれない。



## 16名規模の容量・負荷目安

- 1スペースのメンバー上限は発行者込み16名。承認RPCは親セッション行を `FOR UPDATE` でロックしてから人数を確認するため、同時に複数の承認を行っても上限を超えない。
- 可視タブのポーリングは、各利用者が直近2分以内に操作していれば約5秒間隔、操作が落ち着けば約15秒間隔（どちらも少量のジッターあり）。
- 16名全員が5秒ポーリングを続ける場合は **192要求/分、11,520要求/時、276,480要求/日、約829万要求/30日**。全員が15秒間隔なら **64要求/分、3,840要求/時、92,160要求/日、約276万要求/30日**。
- 変更なし応答だけを想定し、応答JSONを1回150〜500 bytesと置いた概算は、16名が常時5秒ポーリングで約1.24〜4.15 GB/30日、15秒ポーリングで約0.42〜1.38 GB/30日。これはレスポンス本文だけの概算で、HTTP・認証応答や実際の応答サイズは別途 Dashboard で確認する。
- revision が変わると変更なし応答ではなく編成スナップショットを返す。例えば1回の共有編集が30秒ごとに起き、各参加者へ平均1〜10 KBのスナップショットが返る場合、16名分で約1.38〜13.8 GB/30日になる。全ポーリングで上限48 KBのスナップショットが返る極端な上限は約398 GB/30日で、継続的な更新が多い運用では Free の帯域枠を超え得る。
- ポーリング要求そのもののレートはピーク約3.2 RPC/秒なので、16人規模でDB行数も少ない現状では CPU / 同時接続数より、更新頻度とスナップショットの Egress が先に制約になると予想する。
- 2026-10-24 の本番照会では `pg_database_size` が 12,236,467 bytes（約11.7 MiB）。その時点の共有テーブルはセッション0件・メンバー0件・招待0件・申請0件・編集イベント0件だった。DB容量は小さく、16名で通常の編成編集をする短時間の運用は十分現実的と見積もる。ただし常時16名が終日操作する実ストレス試験は未実施であり、保証ではない。
- Supabase Free/Nano を保守的な仮定にした公表枠は、DB 500 MB、Egress 5 GB/月、最大200 pooler clients、DB 接続60、shared CPU・最大0.5 GB RAM。API request 数自体は Pricing 上「Unlimited」だが、実際のボトルネックは request 数より shared compute と Egress。契約プランはプロジェクト一覧APIから確認できないため、Dashboardで要確認。参考: [Supabase Pricing](https://supabase.com/pricing)、[Compute and Disk](https://supabase.com/docs/guides/platform/compute-and-disk)、[Connection pooling and limits](https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits)。利用が毎日長時間続くなら Dashboard の Egress / CPU / connections を監視し、poll 間隔やプランを再評価する。
- 数値はコード上限からの負荷概算で、実測ストレス試験ではない。参照: [Supabase Pricing](https://supabase.com/pricing)、[Compute and Disk](https://supabase.com/docs/guides/platform/compute-and-disk)、[Connection pooling and limits](https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits)。

## 保存先と自動整理ポリシー

- 「共有セッション」は端末のログイン状態や端末管理ではなく、複数人で共有する編成ワークスペースを指す。
- 個人編成はブラウザの `localStorage` / URL に保存され、共有操作をしない限り Supabase に送られない。
- 共有編成の正本は Supabase Postgres。保存対象は人格キー配列、メンバー・権限、招待、参加申請、revision と短期編集イベントであり、人格 JSON 全体や集計 DOM は送らない。
- 認可済みで共有編成を表示中のクライアントの poll を最終利用として記録する。DB 書き込みは同じ共有編成につき最大5分に1回に制限する。
- 30日間 poll がなければ自動アーカイブし、アーカイブから7日後にセッションと子レコードを物理削除する。
- 発行者が手動で終了を確定した場合は、親セッションを即時削除し、CASCADE によりメンバー・招待・申請・編集イベントも同一トランザクションで削除する。手動終了の復元猶予は設けない。
- 自動削除は日次の `pg_cron` ジョブで行う。削除は不可逆なので、UI と手順書に保持期間を明示する。
