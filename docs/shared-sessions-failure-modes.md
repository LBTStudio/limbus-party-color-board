# 共有セッションの失敗想定と対策

この文書は共有セッションの脅威・障害レビューである。共有セッションは Supabase の migration / Anonymous Sign-Ins / publishable key を設定した環境で有効になる。各項目は可能な限りテストへ落とし込み、手動確認だけで済ませない。

| 想定シナリオ | 起きうる問題 | 予防・復旧方針 | 必須テスト |
|---|---|---|---|
| 招待リンクが第三者へ転送される | 第三者がセッションや編成を閲覧する | リンクはアクセス申請だけを許可。承認前は編成・名前・メンバー・履歴を返さない。owner が申請を却下し、リンクを失効できる | 未承認アカウントで状態・一覧・履歴を読もうとすると拒否される |
| 招待トークンが漏れる | なりすまし申請や申請スパム | 十分長い乱数、DB はハッシュだけを保存、期限・失効・レート制限を実装。トークンをログや分析イベントに出さない | 期限切れ／失効トークンの申請が拒否され、ログにトークンがない |
| 招待先が意図した本人とは限らない | 匿名表示名を偽装できる | 表示名は本人確認ではないことを UI に明記。必要なグループでは承認前にメール検証/OAuthを要求する | 未検証アイデンティティを本人確認済みとして表示しない |
| owner が参加者を剥奪する | 古いタブから続けて読書きされる | 読み書きごとにメンバーシップと role を再確認。剥奪後の要求は拒否し、クライアントはローカル表示を閉じる | メンバー剥奪後の poll / write が失敗する |
| セッション A の ID や token を B に差し替える | グループ間で編成が漏れる／混ざる | 全テーブルと RPC を session_id でスコープし、role / membership をサーバー側検証。ID の秘密性だけに依存しない | A メンバーが B の状態・履歴を読まず、B を変更できない |
| viewer が API を直接呼ぶ | UI を迂回して書き込まれる | UI の disable だけに頼らず RLS / RPC で role を検証する | viewer が直接 write RPC を呼んでも拒否される |
| 2人が同時に追加・交換する | 後勝ち上書き、重複、7人以上 | per-session revision と expected_revision をトランザクションで照合し、古い更新を競合扱いにする。キー重複と上限も DB 側で検証 | 並行更新で成功は直列化され、競合側は新状態を受け取る。重複・上限超過が起きない |
| 保存成功後に応答だけ失われる | 再試行で同じ操作を二重適用 | session 単位で unique な operation_id を記録。既に適用済みなら前回結果を返す | commit 後のタイムアウトを模擬し、同じ ID で再送しても二重反映しない |
| クライアントが古い revision で上書きする | 他人の作業が消える | revision 不一致を拒否。最新スナップショットを取得し、無断で再送・マージしない | stale revision の書き込みが拒否され、最新状態が表示される |
| ネットワーク断・API 5xx | 保存したつもりの編集が消える | 「保存中／保存済み／接続なし」を区別。成功応答前は保存済みと表示しない。未送信操作は明示し、勝手に捨てない | API を切断した状態で保存済み表示にならず、復帰後に最新状態へ同期する |
| タブがバックグラウンドで休止し復帰 | 古い表示・複数 poll の重複 | hidden 時はポーリング停止、focus / visibility 復帰時に1回即時同期。in-flight guard で重複を防止 | hidden 中に定期要求が止まり、復帰時に最新 revision を1回取得する |
| 通信のタイミングが全員同じ | poll スパイク、過負荷 | 各タイマーに jitter、重複要求抑止、表示中と非表示を区別 | 複数クライアントの polling が同時刻に固定されない |
| 連続エラーや429 | さらに要求を増やして障害を悪化させる | 指数バックオフ、上限間隔、Retry-After 尊重。招待申請・認証失敗もレート制限 | 連続失敗中に要求頻度が増えず、429後に指定時間を尊重する |
| 共有状態に CDN / ブラウザのキャッシュが返る | 古い編成へ巻き戻る、権限剥奪後の漏えい | セッション API は private/no-store。revision が小さい応答で state を更新しない | cache header と古い応答の逆転を検証する |
| セッションが削除・アーカイブ済み | 復帰時に編集ができない、誤保存 | API が明示的な closed/archived 状態を返し、読み取り専用・閉鎖 UI にする | 削除・アーカイブ後の読み書きが拒否される |
| 人格 DB 更新で古い／無効キーが送られる | 壊れた詳細・不正な編成 | サーバー側の許可キーリストを DB 生成物と同期し、未知のキーを拒否。同期版も必要に応じて記録 | 未知のキー、重複キー、6名超過が拒否される |
| owner が自分を削除する・owner が消える | セッションを管理できなくなる | owner の退出・削除を禁止するか、トランザクションで owner を移譲してから許可する | owner を無管理状態にできない |
| DB/プロバイダーが停止・無料枠が枯渇 | 新規アクセス・保存・poll が停止 | エラーを隠さず表示。保存が確定しないことを示し、必要なら TSV / URL への手動退避を提供。利用量を監視する | 401/403/429/5xx/timeout それぞれが誤って成功扱いにならない |
| 招待リンクへの自動アクセスや連打 | 申請・認証・DB の不要な消費 | 承認前は poll しない。token/session/user 単位のレート制限、低コストな検証、必要なら CAPTCHA を段階導入 | 未承認アクセスが読取ポーリングに到達せず、連打に制限が効く |
| データ削除や誤操作 | 編成・履歴が消える | 編集履歴、owner による削除確認、必要な保持期限を定義。誤操作を考慮して短い undo / 前revision復元を検討 | 削除確認、履歴からの復元手順、保持期限を検証する |

## 優先順位

- **P0（公開前必須）:** 未承認アクセスの遮断、RLS/grants、セッション分離、owner/editor/viewer 権限、revision 競合検出、秘密鍵を静的配信物に入れない。
- **P1（公開前必須の復旧策）:** operation_id による重複防止、切断・復帰状態、招待失効、剥奪、レート制限、非表示タブの poll 停止。
- **P2（運用安定化）:** 操作履歴と復元、使用量アラート、負荷試験、必要に応じた Realtime / 長いポーリングの再評価。

## 境界と残るリスク

- アクセス剥奪で止められるのは**今後のサーバー読み書き**であり、参加者がすでに見た内容のスクリーンショットやコピーは回収できない。
- 共有URLを持つ人はアクセス申請できる設計なので、申請そのものをゼロにはできない。データ閲覧を owner の承認後に限定し、申請の頻度を抑える。
- ポーリングは Realtime message を消すが読み取り要求をなくすものではない。利用量はアクティブユーザー数とタブ表示時間に比例する。無料枠は保証ではなく、実測に基づいて調整する。
- RLS は自動テスト対象。公開スキーマの grant、view、RPC、security definer 関数の search_path を含めてレビューする。service-role key はブラウザへ絶対に出さない。
