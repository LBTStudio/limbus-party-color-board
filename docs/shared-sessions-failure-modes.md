# 共有セッションの失敗想定と対策

この文書は公開閲覧・自由な編集参加へ移行した後の脅威・障害レビューである。閲覧リンクは認証前提にしないため、URLを知っている人が読めることを仕様として扱う。編集権限と公開読み取りを別々に制御し、UIだけでなくサーバーRPC・Realtime RLSで制限する。

| 想定シナリオ | 起きうる問題 | 予防・復旧方針 | 必須テスト |
|---|---|---|---|
| 共有リンクが意図しない相手へ転送される | 第三者が編成を閲覧・編集参加する | 共有リンクをアクセス入口として扱い、発行者が公開閲覧・編集参加を個別に無効化できる。匿名表示名は本人確認ではないことを明記 | 公開閲覧OFF後は未認証読み取りが拒否される。編集OFF後は新規参加が拒否される |
| セッションIDを連番探索される | 公開編成の大量取得 | UUIDを使用し、一覧RPCから全公開セッションを列挙できないようにする。DBテーブルへ直接アクセスさせず、読み取りRPCはセッションIDを一つずつ指定させる | 不正／未知IDは同じ失敗応答となり、セッション一覧や参加者データが返らない |
| 匿名閲覧RPCが大量に呼ばれる | DB CPU・通常Egressが無料枠を圧迫する | 閲覧は初回取得のみで自動pollなし。60秒のタブ内キャッシュと手動更新を使う。公開後は通常EgressとDB負荷を監視。専用CDNキャッシュ／IPレート制限は未実装として扱う | 100・1,000閲覧相当の負荷試験で応答時間・DB負荷・転送量を計測 |
| 読み取りRPCが内部情報を返す | メンバー、編集履歴、別セッションの情報漏えい | SECURITY DEFINER関数で必要最小限のフィールドだけを返す。テーブルへのanon直接権限は付与しない | anonが参加者一覧・編集イベント・別セッションを取得できない |
| 閲覧キャッシュから編集権限が復元される | ログアウト後の古いowner/editor権限でUIが開く | sessionStorageのキャッシュには常にpublic-viewer roleを保存・返却する。書き込みはサーバー側membershipで再検証 | owner/editorで取得後にページ再読込し、キャッシュから書き込み権限が復元されない |
| 編集参加の連打・参加枠超過 | membership行の乱造、スペース容量超過 | join RPCがセッション行をロックし、発行者込み20名・ユーザーごと20スペースを検証する。Anonymous AuthにTurnstileを併用できる | 同時joinでも上限を超えず、既存memberの再参加で重複行が作られない |
| ownerが特定編集者を解除する | 公開リンクから同じAuth IDが再参加する | `remove_party_session_member` が `session_access_requests.status='revoked'` の拒否記録を残し、join RPCが照合する。表示名でなくAuth user IDで判定する。ただし本人確認ではないため、別端末・ブラウザデータ削除後の新しい匿名IDまでは遮断できない | 解除した同じ匿名Auth IDは再参加できず、新しいIDは公開編集ONなら参加できることを確認する |
| ownerが既存スペースを移行する | 旧来の非公開セッションが自動的に公開される | 新規カラムの `DEFAULT false` で既存スペースは非公開のまま維持する。移行で既存行を上書きしない。DB関数で作成した新規スペースも両方falseで開始し、新UIが作成直後にowner専用RPCで公開・編集を有効化する。旧UIからの作成は非公開のまま | 既存セッションはanon readで拒否され、ownerのみ読取・設定変更できる。新UIから作成した場合だけ公開フラグtrueになる |
| 編集参加が無認証で直接呼ばれる | membershipの偽造 | join RPCはauth.uid()を必須にし、SECURITY DEFINERのサーバー処理だけでmembershipを作る。anonには実行権限を与えない | anonロールでjoin RPCを呼ぶと拒否される |
| 閲覧者がwrite RPCを直接呼ぶ | UI制御を迂回して編集する | apply_party_edit_v2が毎回membership/roleを検証する。read-only public RPCは書き込み処理を持たない | public-viewer / anonからwrite RPCを呼んでも拒否される |
| 発行者が公開編集を停止する | 既存メンバーまで意図せず退出させる | 公開編集フラグは新規join RPCだけを止め、既存membershipとwrite権限は維持する。特定メンバーの解除は別のowner専用RPCを使う | 編集OFF後の新規joinだけが拒否され、既存editorの保存・同期は継続する |
| 発行者が公開閲覧を停止する | 新しい訪問者がデータを取得する／既存キャッシュが残る | read RPCは新規anon取得を拒否する。認可済みowner/editorは管理のため読取継続可能。既に取得されたデータや60秒のブラウザキャッシュは回収できないことを説明する | anonの新規取得が失敗し、既存memberの再読取は許可される |
| Broadcastが別セッションへ流れる | 編成更新通知の混線 | topicを `party:<session UUID>` に分け、private channelのRLSで同じセッションのowner/editorだけを許可する | AのeditorがBのtopicへ接続できず、Bのrevisionを受け取らない |
| Broadcast payloadに編成データが入る | Realtimeメッセージ量・内容漏えい | DB triggerはrevisionだけを送信し、編成本体は認可付きRPCから必要時に取得する | trigger payloadにparty_keys/party_personasが含まれない |
| Realtimeの認可がメンバー剥奪後も残る | 古いWebSocketが通知を受け続ける | Supabaseは接続時にRealtime RLSを評価するため、membership削除が既存socketを即時切断するとは限らない。書き込みRPCで再確認し、通知payloadはrevisionだけに限定する | 参加権限を削除した後、古いタブのwriteが必ず拒否される |
| Realtimeが停止・接続上限に達する | 編集画面が同期しない | 編集者のみRealtimeへ接続し、30/60秒pollへフォールバックする。hidden時は接続を停止。閲覧者にはRealtime接続させない | Realtimeを遮断し、編集画面がpollへ切り替わり、閲覧者の通信量が増えない |
| 2人が同時に編集する | 後勝ち上書き、重複、上限超過 | per-session revision、expected_revision、unique operation_idをトランザクションで検証する | stale revisionが競合となり、同じoperation_idの再送で二重反映しない |
| 保存成功後に応答だけ失われる | 再試行で同じ操作を二重適用 | operation_idで冪等性を確保し、成功応答前は保存済み表示にしない | commit後のタイムアウトを模擬し、同じIDの再送で二重反映しない |
| ブラウザタブが休止・復帰する | 古い表示、接続の重複 | hidden時はRealtime/pollを停止し、復帰時にrevision確認後に再接続する | hidden中に定期通信が止まり、復帰時に同期が再開する |
| セッションAのIDをBへ差し替える | 他グループの編成・設定へアクセス | すべてのRPCにsession_idを明示し、owner/memberと公開フラグをサーバー側で検証 | AのメンバーがBの状態を読まず、Bを変更できない |
| 追加人格スナップショットが大きすぎる | Egress・DB容量・応答時間の増大 | 選択された編成分だけを保存し、最大20件・合計60KBの上限を維持。LBT生セーブは送信しない | 60KB超過、無効な型、未選択人格のスナップショットを拒否 |
| 無料枠・DB負荷が閾値へ到達 | 閲覧・保存・Realtimeが停止または遅延 | Egress、Realtime Messages、Peak Connections、Database Size、DB CPUを監視。80%で警戒、95%で公開編集・取得の抑制を検討する | 80/95%相当の警告条件と、API障害時に成功表示しないことを確認 |
| 発行者がスペースを終了する | 共有編成・メンバー・招待・申請・編集履歴が失われる | 明示確認後は即時物理削除。確認ダイアログで復元不可を明示し、個人編成と区別する | 終了後に共有行が削除され、個人編成は残る |
| 30日間誰も開かない | 古いスペースが残り続ける | 30日後に自動終了、さらに7日後に日次ジョブで物理削除 | 自動終了と7日猶予の動作を個別に検証 |

## 負荷試験で記録する値

- 閲覧: 1/20/100/1,000クライアント相当の初回取得、手動更新、キャッシュ利用時のRPC数・応答bytes・DB CPU・p95応答時間
- 編集: 1/5/20接続の保存回数、1保存当たりのRealtime Messages、ピーク接続、poll fallback時のRPC数
- 追加人格: 空編成・公式人格のみ・追加人格あり（上限近く）の応答bytes
- 失敗系: 401/403/429/5xx、timeout、Realtime切断、無料枠到達時のUI表示

Nodeの静的テストはSQL文字列・権限条件の確認であり、実Supabaseの負荷試験やRLS実行を代替しない。実Supabaseへmigrationを適用した後に、上記の実測を行う。
